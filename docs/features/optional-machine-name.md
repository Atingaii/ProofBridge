# Optional machine name

## Goals

The Settings add-endpoint flow accepts an optional machine display name. A
user-supplied name is passed to the existing `link --name` flag. Blank input
keeps the existing default generated by `link.go:defaultLinkName`.

## Non-goals

No rename API, database migration, WebSocket protocol extension, identity change, session
or orchestration change, endpoint upgrade, or cross-platform package release.

## Data and protocol impact

Reuse the existing naming input and add an optional `name` request field in
`internal/hub/server.go:handleCreateBridgeToken`. Preserve the existing token
`label` semantics. Only the explicit trimmed `name` (bounded to 80 Unicode
characters) becomes the generated command's optional name. Old clients that
send only `label`, including their default labels, retain default CLI naming.
Reuse the existing shell quoting in
`internal/hub/server.go:bridgeConnectArgs`, CLI name persistence in
`link.go:prepareLinkOptions`, registration and Store agent name update.
Repair commands continue to use the existing agent name and machine identity.

## Implementation steps

1. Propagate the explicit optional name through token response command options.
2. Relabel the existing input and explain the default behavior in both languages;
   send blank input as an empty name and keep the fallback label token-only.
3. Verify all permission-mode commands, shell quoting, blanks and repairs.
4. Build target frontend editions and the native Hub, back up deployment,
   publish authorized websites and verify public health/resources.

## Exit gates

- Explicit names survive shell argument parsing, including Chinese, spaces,
  single quotes and shell metacharacters.
- Blank or whitespace input emits no `--name`; repair preserves the agent name.
- Frontend checks/builds, Go tests/build and `make doc-lint` pass.
- Website deployment retains database/configuration/identity and old static
  roots; does not restart Bridges or replace non-native endpoint packages.

## Compatibility contract

### Scope and signatures

`POST /api/bridge-tokens` accepts the existing `label` and
`permissionProfile` plus optional string `name`. Response keys are unchanged.
The generated `link --name` flag and registration Name payload already exist.

### Validation and cases

| Request | Command behavior | Token label |
| --- | --- | --- |
| `{"label":"wsl2-cli"}` (old client) | No `--name` | `wsl2-cli` |
| `{"label":"wsl2-cli","name":"   "}` (blank) | No `--name` | `wsl2-cli` |
| `{"label":"工作电脑","name":" 工作电脑 "}` | `--name '工作电脑'` | `工作电脑` |
| Name longer than 80 Unicode characters | Trim, then truncate to 80 characters | Independent existing label normalization |
| Invalid JSON or non-string name | HTTP 400 `BAD_REQUEST` | No token created |

Names containing shell metacharacters are literal arguments through
`internal/hub/server.go:shellQuote`. Existing permission validation is unchanged.

### Required tests and wrong versus correct

`internal/hub/bridge_token_name_test.go:TestBridgeTokenOptionalMachineName`
checks all permission-mode commands, actual shell argument parsing, blank and
legacy requests, Unicode limits, independent label/name, and persisted token
labels. `TestBridgeRepairTokenPreservesMachineNameAndIdentity` checks the repair
name, machine ID, directory and unchanged agent record.

Wrong: infer a machine name from a nonempty token label; old forms synthesize
labels even when the user leaves the input blank. Correct: only an explicit
`name` becomes `--name`; repair commands prefer the existing agent name.

## Reviewer Q&A

**Does a display name change machine identity or history?** No. Identity stays
the existing machine ID, independent of the display name.

**Why a separate optional request field?** The add-endpoint form already has
one naming input and reuses it for both label and name. Old clients synthesize
a nonempty token label for blank input, so interpreting label as a name would
change their default behavior. A separate optional `name` preserves backward
compatibility without a new form or response shape.

**Are old Bridges compatible?** Yes. The existing `link --name` implementation
already persists and sends the name. This feature adds no new CLI flag.
